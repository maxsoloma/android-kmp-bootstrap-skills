# Design

## Context

See proposal.md for motivation. The Kotlin CLI currently has one Options model,
strict JSON resolution, five presets, a six-step wizard, modern/hardened renderers,
spec/lock planning and 31 tests. Modern baseline renders have golden inventories;
hardened profiles own fixed DI and Navigation Compose 2 integrations. The previous
OpenSpec change is complete but not synced/archived; its iteration-one limitations
are extended explicitly here.

## Goals / Non-Goals

Goals: real SwiftUI plus shared logic; usable DI and navigation examples; one
compatibility model and transparent verification for terminal/agent/config entry
points. Existing calls retain exact default generated bytes.

Non-goals: modern Hilt integration, hybrid SwiftUI/CMP UI, arbitrary third-party
recipes, new storage/network stacks, UI automation framework, automatic SDK setup.
Hilt stays discoverable through hardened Android; it is not offered as a working
modern/shared recipe.

## Decisions

- Extend v1 config with `di` and `navigation`; `ui=swiftui` identifies native mobile.
  Existing defaults stay manual/none, android-compose or shared-compose. Hardened
  choices resolve to their existing Hilt/Koin and navigation-compose stack and
  reject changes. New flat flags use the same compatibility rules as JSON.
- SwiftUI requires modern KMP and iOS, optionally Android; desktop/web are rejected.
  Add a sixth preset without renumbering the existing five. Add a UI menu and DI /
  navigation menus; editing retains explicit choices and exposes incompatibilities.
- DI uses manual composition or isolated koin-core 4.2.2 bindings, not a global
  process context. Each controller owns its graph and closes it. No annotation
  processor or new generator runtime is needed. Shared counter tests exercise
  graph construction, incrementing and independent lifetimes.
- Navigation options are `none`, `navigation3` (Compose UI), `platform-native`
  (SwiftUI NavigationStack and Android Navigation 3). Navigation 3 uses stable
  org.jetbrains.androidx.navigation3:navigation3-ui 1.1.2 with Kotlin serialization
  1.11.0 and explicit polymorphic route serializers for non-JVM targets. Shared
  browser navigation does not promise browser history synchronization.
- Native shared module contains only Kotlin business logic and an exported
  no-argument counter controller. Android owns its Compose state; SwiftUI owns an
  ObservableObject with Published state and calls the same controller. No Compose
  iOS bridge or shared coroutine/ViewModel bridge. A JVM logic test target allows
  testing this UI-free module without Xcode. Native UI with no navigation retains
  iOS 15.0; platform-native navigation requires explicit iOS 16.0 or newer.
- Keep baseline rendering unchanged and apply additive stack rendering only for
  SwiftUI or nondefault modern components. Pins live in a separate packaged
  component catalog so existing bootstrap.json toolchain bytes do not change.
  Normalized specs/locks capture new selections; old locks remain tied to the old
  resource bundle, as documented by iteration one.
- Plans include scopes/pins, shared test commands and an Xcode simulator app build
  command. Existing verify remains compilation/unit/framework-oriented; it reports
  an additional unexecuted Xcode application check for SwiftUI. Full Xcode is not
  installed locally; never claim Swift typechecking or UI runtime success from
  template or plist checks.

## Risks / Trade-offs

- New library transitives may require newer platform levels → inspect published
  Gradle module metadata and run Android/desktop/Wasm builds before finalizing pins.
- Swift ABI and host integration cannot be compiled without Xcode → preserve the
  existing direct-integration project and report the missing app/framework checks.
- New wizard prompts change scripts that feed terminal input → agents use JSON,
  and terminal tests explicitly cover the updated flow and cancellation.
- Default output preservation constrains refactoring → keep golden fixtures and
  run all existing regressions unchanged; new integration tests cover new branches.

## Migration Plan

Rebuild the three identical standalone JARs and update skill/docs together. Old
configs without new fields continue to work. No existing application is modified.
Rollback uses the preceding skill bundle; lock mismatch remains explicit.
